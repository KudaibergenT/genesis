# Измеренный разбор сбоев

Каждый пункт: что измерили, причина, исправление и повторная проверка (тест или команда, которые
воспроизводят результат). Пункт 9 — неустранимый предел официальной формулы.

## 1. Matcher расходился с опубликованными соглашениями жюри

Измерено скриптом на одинаковых входах для тега `stage-3` и текущего кода (truth: одна ошибка A,
affected={R1}, 10000 KZT, доказательства {D1, D2}, τ=0; inspection_steps=10):

| вход | stage-3 | сейчас | ожидание жюри |
|---|---|---|---|
| M04: evidence = [D1, D2, U], U не существует | TP=1, reward 0.98 | TP=0, FP=1, reward −1 (`unknown_evidence`) | FP |
| M06: currency = "kzt" | весь submit невалиден, −1 | FP=1, reward −1, submit валиден | FP, не авария |
| правильный F + F с type="fraud" | весь submit невалиден, −1 | TP=1, FP=1, reward 0.3133 | FP, не авария |
| M10: F0 подходит A и B, F1 только A | `ValueError: truth keys must be unique` | TP=2, reward 0.98 | TP=2 |

Причина: схема считала неизвестный тип, валюту не по шаблону `^[A-Z]{3}$`, отрицательную сумму и
пустой affected_ids структурными ошибками; доказательства проверялись только на включение
допустимого набора; matcher был жадным и требовал уникальный ключ (type, affected_ids).
Исправление: `evaluator/schema.py` (структурные ошибки — только тип значения, отсутствие поля и
лимиты), `evaluator/matcher.py` (максимальное паросочетание с детерминированным выбором по
(issue_id, индекс), все evidence_ids обязаны существовать в открытых данных).
Повторная проверка: `tests/test_judge_checks.py` — тесты 1–20 блока 3 и примеры M01–M12.

## 2. Адаптер подтверждал повторный submit после завершения эпизода

Найдено тестом C15: второй submit после `terminated=true` получал `{"accepted": true}`, хотя среда
вернула `episode_finished` (findings и счёт не менялись, но ответ вводил в заблуждение).
Причина: трансляция ответа submit не проверяла код ошибки. Исправление: `judge_adapter.py`,
`_observation`. Повторная проверка: `test_c15_submit_is_final`, `test_c17_hundred_actions_truncate`.

## 3. Генератор молча вносил меньше ошибок, чем запрошено

Измерено: 5 из 520 эпизодов (`suites.exactly(k)`, 40 сидов на k) получали меньше k ошибок; все пять
— сценарии взаимодействия на мирах без валютного счёта с остатком или без валютного поступления в
периоде; порог заметности FX был ≥ 1 основной единицы базовой валюты.
Исправление: порог max(20·τ, 0.1% суммы); в мультивалютной компании ≥ 6 валютных счетов, два
открытых и два оплаченных в периоде; в provenance счётчики `requested/granted/injected` по оператору.
Повторная проверка: 0 из 1040 (80 сидов на k), сейчас 0 из 390 на генераторе 0.3.0;
`tests/test_stage2.py::test_generator_supports_every_issue_count_from_0_to_12`.

## 4. Состояние до инъекции нельзя было восстановить по provenance

Причина: номера счетов и платежей назначались подряд по дате для всех документов, поэтому вставка
дубля с новым номером сдвигала номера последующих счетов — «до» и «после» отличались не только
изменёнными записями. Исправление: «чистые» номера назначаются с естественными пропусками и не
зависят от внесённых ошибок; `provenance.changes` содержит все добавленные, удалённые и изменённые
записи с полными значениями до и после. Повторная проверка: восстановление по `changes` совпало с
независимо сгенерированной чистой книгой в 390 из 390 эпизодов (k = 0…12) и проходит все
бухгалтерские равенства; `tests/test_judge_checks.py::test_matrix_episode_is_correct`.

## 5. Защита процесса агента ломала импорт модулей

Измерено: атакующий агент `attack_read_files` вместо попыток чтения выдал 100 шагов
`policy_error` — `import pathlib` внутри агента падал с `ModuleNotFoundError: urllib.parse`.
Причина: audit hook блокировал `os.listdir` целиком, а импортёр Python читает каталоги
стандартной библиотеки. Исправление: листинг разрешён только внутри стандартной библиотеки и кода
пакета (`sandbox/guard.py`). Повторная проверка: 21 локальная попытка атаки заблокирована, импорты
работают — `tests/test_isolation.py::test_agent_cannot_read_truth_provenance_or_the_filesystem`, в том
числе в контейнере.

## 6. Независимая проверка зависела от порядка `affected_ids`

Измерено: первый прогон 20 парных проверок в стиле жюри (`scripts/paired_checks.py`) — 18/20; в
P06 и P08 (дубль счёта, смена ID) `checks.verify_episode` на копии сообщал «affected_ids not
canonical», хотя метрики oracle и решателя совпали. Причина: преобразование, как у жюри, сохраняет
порядок списков, и после переименования `affected_ids` перестают быть отсортированы; проверяющий
сравнивал их как кортеж, а matcher всегда — как множество. Прежний парный тест этого не видел: его
преобразователь сортировал списки. Исправление: `checks.verify_episode` и `audit` сравнивают
`affected_ids` как множество (ошибка — только повтор ID). Повторная проверка: 20/20,
`tests/test_paired.py`.

## 7. CSV и JSON по-разному представляли отсутствующие ссылки

В CSV отсутствующая ссылка была пустым полем, в JSON — `null`; требование кейса — «явные null».
Исправление: в CSV пишется токен `null`, пустое поле отвергается загрузчиком, `null` разрешён только
в ссылочных колонках журнала; представление записано в manifest и policy. Повторная проверка:
`tests/test_csv_null.py` (запись → чтение → запись побайтно совпадает, JSON-наблюдения содержат
`null`, пустые поля и `null` в обязательных колонках отвергаются).

## 8. Контейнерная проверка падала на нативных Linux-раннерах CI

Измерено: первый прогон `.github/workflows/docker-multiarch.yml` (run 44787035414) — оба задания
(`ubuntu-24.04` x86_64 и `ubuntu-24.04-arm` aarch64) упали на шаге контейнерной проверки, артефакт
пуст («No files were found with the provided path: results/docker_run_all/»). Локально на Docker Desktop
этого не было. Воспроизведено на Docker-томе с настоящими Linux-правами: каталог `/out` владельца
uid 1001 с правами 0755 → `PermissionError: [Errno 13] Permission denied: '/out/run_all.json'` и три
проваленные проверки. Причина: оценщик в контейнере — root со сброшенными capabilities (без
`CAP_DAC_OVERRIDE`), а смонтированный каталог отчёта принадлежит пользователю раннера; Docker Desktop
на macOS права монтирования не проверяет. Исправление: `scripts/docker_run_all.sh` делает каталог
отчёта 0777 (capabilities контейнера не расширяются). Повторная проверка: тот же том с 0777 —
0 провалов; регрессионный тест `tests/test_docker.py::test_report_directory_owned_by_another_user`;
повторный прогон CI — в `jury_audit_report.md`.

## 9. Оценщик падал на truth.json только с полями §03

Измерено (аудит 2026-11-20, `scratchpad/audit_probe.py`): фикстура, в truth которой ровно поля §03
(`issue_id`, `type`, `affected_ids`, `expected_amount_minor`, `currency`, наборы доказательств), без нашего
`tolerance_minor` → `score_episode` бросал `KeyError: 'tolerance_minor'` вместо метрик. Это затронуло бы
все 20 тестов блока 3, если жюри соберёт фикстуры по схеме кейса. Причина: matcher читал
`issue["tolerance_minor"]` напрямую, а генератор всегда писал это поле, поэтому тесты на наших
эпизодах сбоя не видели. Исправление: `src/auditenv/truth.py` проверяет truth по
`schemas/truth_input.schema.json`, отсутствующий τ = 0 (умолчание жюри), отсутствующий `episode_id`
берётся из manifest, разрешён голый список ошибок, некорректный truth → `TruthFormatError` с
перечнем нарушений. Повторная проверка: `tests/test_truth_contract.py` — фикстура только с полями
§03 для `duplicate_invoice` и `fx_conversion` даёт точные значения тестов 1, 2, 5–11, 15–17 блока 3;
явный τ = 1 даёт TP для 10001 и FP для 10002 (M08); проверка `judge/truth_contract_section03_fixtures`
в `run_all` на обеих архитектурах.

## 10. В образе не было каталога схем

Измерено: после добавления `schemas/` хостовый pytest прошёл, а `tests/test_docker.py::
test_quick_offline_evaluation_passes_inside_the_container` упал: в контейнере
`[FAIL] judge/json_schema_conformance`, `'/app/schemas' == '/app/src/auditenv/schemas'`. Причина:
Dockerfile копирует каталоги поимённо, `schemas/` (символическая ссылка в git) в образ не попал.
Исправление: `COPY schemas ./schemas`; тест сравнивает содержимое корневого `schemas/` с пакетным
побайтно, а не требует ссылку (ссылка не переживает копирование в образ и клон на Windows).
Повторная проверка: в контейнере `tests/test_schemas.py` 85/85, полный `scripts/docker_run_all.sh`
на arm64 и amd64 — `ok: true`, 0 провалов.

## 11. Неустранимый предел: «пометить всё» при k ≥ 10

Официальная формула даёт ответу из 30 выводов, содержащему все k истинных, награду (3k − 30)/(30 + k):
0 при k = 10, +0.073 при k = 11, +0.143 при k = 12. Формула не меняется; реальная политика
`flag_everything` получает −1 при любом k, а такой ответ строго хуже честного. Воспроизведение:
`make reward-analysis` → `docs/reward_analysis.md`; `tests/test_reward_analysis.py`.
