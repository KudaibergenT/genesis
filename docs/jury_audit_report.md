## 2. Парные проверки (блок 4, 15 баллов)

Распределение по определениям: P01–P05 — перестановка (D01–D05), P06–P10 — замена ID (D06–D10),
P11–P20 — перестановка и замена ID (D11–D20). Эпизоды D01–D20 генерируются через
`judge_adapter.generate_episode` с конфигурациями `configs/scenarios/*.json` и фиксированными seed
(`auditenv.suites.JUDGE_MATRIX`).

Преобразование (`src/auditenv/paired.py`) пишет новую копию эпизода, исходный не меняется:
перестановка строк `ledger.csv`, документов `invoices.jsonl`/`payments.jsonl` и строк `fx.csv`
(порядок `line_items` сохраняется); взаимно однозначная замена `row_id`, `doc_id`, `invoice_id`,
`payment_id`, `entity_id` во всех файлах, ссылках (`invoice_refs`), truth и provenance; новое название
компании в manifest. Ключи курсов `date|source|target` не меняются (по правилам жюри это не
суррогатные ID). Оба варианта подаются в `reset` через `episode_dir` с одинаковым seed.

Для каждой пары проверено и выполнено во всех 20:

| свойство | как проверяется |
|---|---|
| строки журнала и документы переставлены | порядок ID после обратного отображения отличается |
| заменены row_id, doc_id, invoice_id, payment_id, entity_id | в каждом пространстве > 0 замен; ни одного старого ID в файлах копии и в наблюдениях |
| название компании изменено | manifest копии |
| число и типы эталонных ошибок | совпадают |
| `affected_ids`, суммы, валюты, наборы доказательств | совпадают после обратного отображения ID |
| доказательства остаются достаточными | `checks.verify_episode` на копии — без проблем; книги до инъекции по `provenance.changes` копии проходят все равенства |
| oracle отвечает новыми ID | все `affected_ids` и `evidence_ids` ответа существуют в открытых данных копии |
| TP, FP, FN, P, R, F1, reward | совпадают при одинаковом числе исследовательских шагов (4): F1 = 1.0, reward = 0.992 |
| эталонный решатель в изолированном процессе | метрики и награда совпадают; найденные выводы совпадают после обратного отображения |
| воспроизводимость | два прогона на исходном и два на копии дают одинаковые транскрипты и оценки |

Найдено и исправлено: на первом прогоне 18/20 — независимая проверка сравнивала `affected_ids`
с учётом порядка (см. `failure_analysis.md`, п. 6).

## 3. Представление null (CSV и JSON)

Единое представление: отсутствующая ссылка — явный null; в CSV — токен `null` без кавычек, в
JSON/JSONL и наблюдениях — JSON `null`. Пустое поле CSV — ошибка формата; `null` разрешён только в
`entity_id`, `invoice_id`, `payment_id` журнала. Записано в `manifest.null_representation` и
`policy.ledger.null_references`. Тесты (`tests/test_csv_null.py`, 7): запись → чтение → запись
побайтно совпадает; число токенов `null` равно числу отсутствующих ссылок; наблюдения содержат JSON
`null`; загрузчик отвергает пустые поля и `null` в обязательных колонках; писатель отвергает
неоднозначные значения. Версия генератора поднята до 0.3.1, открытые эпизоды перегенерированы.

## 4. Архитектуры

| платформа | способ | результат |
|---|---|---|
| linux/arm64 | нативно (Docker Desktop, Apple Silicon) | 38/38, `machine = aarch64` |
| linux/amd64 | эмуляция x86-64 в Docker Desktop на Apple Silicon | 38/38, `machine = x86_64` |
| linux/amd64 на нативном x86-64 | `.github/workflows/docker-multiarch.yml`, раннер `ubuntu-24.04` | **не запускалось** (нужна публикация репозитория) |
| linux/arm64 на нативном Linux arm64 | тот же workflow, раннер `ubuntu-24.04-arm` | **не запускалось** |

Оценки и траектории базовых политик в arm64- и amd64-контейнерах совпадают побайтно (SHA-256
итогов без времени выполнения и траекторий одинаковы), golden-хэши эпизодов воспроизводятся на обеих
платформах. Базовый образ закреплён по digest мультиархитектурного манифеста
`python:3.11-slim@sha256:07d48240…`; тестовые зависимости — чистые Python-колёса с хэшами.

## 6. Непроверенные требования и риски

1. **Нативный x86-64 и нативный Linux arm64 не проверены.** amd64 проверен только под эмуляцией;
   CI-процесс написан, но не запускался — для него нужна публикация репозитория (жду разрешения).
   Доступность раннера `ubuntu-24.04-arm` подтвердится только первым запуском.
2. **Инструменты жюри не запускались.** Парные преобразования и независимая сверка блока 2
   выполнены нашей реализацией опубликованных правил; скрипты и машина жюри не опубликованы.
   Время эпизодов измерено на нашей машине; характеристики машины жюри объявляются отдельно.
3. **Изоляция политик жюри — на их стороне.** Наш адаптер в закрытом режиме не загружает эталон в
   объект среды; процесс политики жюри запускает сам. Собственный изолированный раннер
   (`auditenv.sandbox`) проверен отдельно и в контейнере работает под uid 10001.
4. **Вне Docker** нет разделения прав ОС и запрета сети на уровне ядра (см. design_note).
5. **Демо** из списка сдачи как отдельный сценарий показа не оформлено; работа среды демонстрируется
   командами `python3.11 -m auditenv run --policy reference_solver --seed 1002` и `scripts/run_all.py`.
6. **Предел официальной формулы:** при k ≥ 10 ответ из 30 выводов со всей правдой даёт reward ≥ 0
   (`docs/reward_analysis.md`); формула не менялась.
7. **Публикация:** репозиторий не опубликован, изменения закоммичены только локально.
